## 一、集成工作内容

本次围绕需求升级 A 与迭代 2 的上线目标，完成前端 7 个页面与后端接口的整体对接。前后端原有契约并不一致（请求路径、参数名、状态表示均不同），集成采用「单点适配」方式：后端代码与页面代码均不做改动，全部差异集中在 `frontend/js/api.js` 适配层，出现问题时可以单点回滚。

| 页面功能 | 适配层方法 | 对接的后端接口 | 集成处理要点 |
|---|---|---|---|
| 商品详情 | `Api.getProductDetail` | `GET /api/products/current` | 后端状态枚举映射为页面数字状态，无在售商品返回空态 |
| 提交购买意向 | `Api.submitOrder` | `POST /api/intents` | 字段改名（buyerPhone→contact、remark→note），迭代 2 改为排队制 |
| 卖家登录 | `Api.sellerLogin` | `POST /api/admin/login` | 后端不返回令牌，适配层补发本地登录态 |
| 商品列表 | `Api.getProductList` | `GET /api/admin/products` | 合并当前与历史商品，过滤 DRAFT 草稿，下架显示为「手动下架」 |
| 发布商品 | `Api.addProduct` | `POST /api/admin/products` 与 `/{id}/publish` | 发布前预检在售状态，失败不留脏数据 |
| 手动冻结 / 下架 | `Api.freezeProduct`、`Api.offlineProduct` | `POST /api/admin/products/{id}/withdraw` | 下架同时作废该商品的排队意向 |
| 恢复上架 | `Api.restoreProduct` | `POST /api/admin/products/{id}/publish` | 按商品当前状态选择恢复路径 |
| 订单列表 | `Api.getOrderList` | `GET /api/admin/products/{id}/intents` | 汇总各商品意向，映射买家信息与订单状态 |
| 标记交易结果 | `Api.updateOrderStatus` | `POST /api/admin/products/{id}/freeze` 与 `POST /api/admin/trades/{id}/finish` | 成交前先冻结，成交后自动补货 |
| 口令码查询 | `Api.queryIntent` | `POST /api/intents/lookup` | 交易进度映射，口令失效统一提示 |
| 修改密码 | `Api.updatePassword` | `PUT /api/admin/password` | 校验两次新密码一致 |

## 二、集成验收用例

自动化验收覆盖正常流程、业务规则约束与异常分支，共 10 组用例、36 项断言。

| 编号 | 测试模块 | 输入或操作 | 验证标准 |
|---|---|---|---|
| I-T01 | 商品详情 | 查询当前商品，并按编号查询历史商品 | 状态映射正确，名称价格描述图片字段完整 |
| I-T02 | 商品列表 | 加载后台商品列表 | 当前与历史合并、按编号倒序、草稿不显示 |
| I-T03 | 卖家登录 | 使用正确密码与错误密码各登录一次 | 成功写入登录态，失败提示中文错误 |
| I-T04 | 发布约束 | 已有在售商品时发布新商品 | 发布被拒绝，提示中文文案，不产生脏数据 |
| I-T05 | 意向排队 | 提交购买意向 | 返回口令码，商品保持「在售」允许后续排队 |
| I-T06 | 订单列表 | 查询后台意向订单 | 买家姓名、电话、备注与状态映射正确 |
| I-T07 | 标记成交 | 将排队意向标记为成功 | 先冻结再结算，商品转为「已售」 |
| I-T08 | 自动补货 | 成交后查询当前商品 | 自动生成同款新商品并处于在售状态 |
| I-T09 | 手动下架 | 提交意向后手动下架并再次查询口令码 | 商品转「手动下架」，排队意向转「意向失效」，口令查询提示失效 |
| I-T10 | 密码与登录态 | 使用错误原密码修改、登出 | 改密被拒绝，登录态正确清除 |
