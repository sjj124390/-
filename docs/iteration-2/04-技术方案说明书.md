## 二、系统结构

买家前台 / 卖家后台 → Spring Boot HTTP接口 → MySQL 数据库。

- 前端负责表单校验、状态展示与二次确认。
- 后端负责身份校验、业务判断和事务控制。
- 数据库负责持久化、关联约束及关键唯一性约束。
- 前后端使用 JSON 交互，沿用现有项目接口风格。

## 三、核心数据模型

沿用现有四张业务表：

| 数据表 | 作用 |
|---|---|
| seller | 卖家账号与密码哈希 |
| product | 商品信息、在售与历史状态 |
| purchase_intent | 买家购买意向、查询口令摘要与意向状态 |
| offline_trade | 已选择意向的线下交易及结果 |

商品状态沿用现有枚举 DRAFT、ON_SALE、FROZEN、SOLD、OFF_SHELF，手动下架使用 OFF_SHELF，交易冻结使用 FROZEN，不应混用。

SQL文件：[database/schema.sql](https://github.com/sjj124390/-/blob/main/database/schema.sql)。

## 四、本轮设计重点

### 1. 商品手动下架

拟采用后台操作接口，核心判断步骤：

1. 核验卖家身份。
2. 检查商品是否仍在售，是否有进行中的交易。
3. 前端给出“未成功意向将失效，系统不会通知买家”的二次确认。
4. 后端在同一事务中将商品由 ON_SALE 改为 OFF_SHELF，并取消其未成功的购买意向。
5. 返回处理结果，前端刷新商品列表和状态。

发生并发冲突或事务失败时应回滚，不能留下商品已下架但购买意向仍可成交的状态。

### 2. 交易冻结与手动下架分离

- FROZEN：代表交易流程占用商品，须先处理交易结果。
- OFF_SHELF：代表卖家主动停止出售，进入历史。
- 交易中商品不允许跳过交易处理直接手动下架。

### 3. 接口设计

| 操作 | 建议接口或既有路径 | 说明 |
|---|---|---|
| 商品列表 | GET /api/admin/products | 查询管理端商品及状态 |
| 创建商品 | POST /api/admin/products | 创建商品草稿 |
| 发布商品 | POST /api/admin/products/{id}/publish | 满足条件后发布 |
| 手动下架 | POST /api/admin/products/{id}/withdraw | 仅在售商品，业务事务处理 |
| 查询意向 | GET /api/admin/products/{id}/intents | 查询该商品意向 |
| 处理交易 | POST /api/admin/trades/{id}/finish | 按交易结果更新状态 |
| 口令查询 | POST /api/intents/lookup | 返回意向状态，不公开联系方式 |

注：上表为目标接口或原有技术方案路径；实际接口须与现有 FacadeController 和前端调用契约核对，不表示本轮均已实现。

### 4. 前端改动

商品管理页区分“交易冻结”和“手动下架”，对下架操作增加二次确认。下架成功后刷新商品与历史列表，并将不可购买商品的购买入口置为不可用。

### 5. 数据库改动

优先复用现有表结构，不新增无必要的数据表。检查商品状态、购买意向状态和交易记录的关联；为手动下架提供单事务状态更新，并在冲突时拒绝非法状态转换。

## 五、测试与交付

计划验证：

1. 在售商品下架成功；前台不可再购买。
2. 交易中禁止直接下架。
3. 下架后待处理意向与查询口令失效。
4. 下架商品保留历史，新商品可正常发布。
5. 并发下架/购买意向提交不产生不一致数据。
6. 未登录用户无法直接调用敏感后台接口。

以上为待验证事项；旧仓库历史测试报告不能作为本轮新增功能已通过的证明。
