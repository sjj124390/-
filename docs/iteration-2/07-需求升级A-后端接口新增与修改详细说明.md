# 需求升级 A——后端接口新增与修改详细说明

**课程项目：** 在线购物系统  
**提交组：** 第10组  
**汇报人：** 孙俊杰  
**日期：** 2026年11月12日  
**工作范围：** 后端接口设计、原有接口调整及业务规则说明

## 一、本次接口调整的背景与目标

本次需求升级 A 分为**商品管理升级（A.1）**与**客户管理升级（A.2）**。原有系统主要面向单卖家、单件在售商品与线下购买意向处理，已经具备商品发布、购买意向提交、交易成功/失败处理、卖家登录等接口。升级后，后端需要在原有基础上支持多商品在售、二级分类、关键词搜索、分页、库存数量、多图片、客户注册登录、个人历史订单及商家查询客户交易记录。

本次工作以现有 Spring Boot 项目为基础，遵循“**能复用的接口继续复用，业务发生变化的接口修改，原来没有的能力新增接口**”的原则。接口统一以 `/api` 开头，返回沿用现有 `Result<T>` 格式：`code`、`message`、`data`。

**范围说明：** 本文是针对需求升级 A 的后端接口变更说明，明确新增内容和原接口需修改的内容；现有仓库代码仍按其实际实现为准。本文不涉及前端页面、数据库脚本交付、Docker 构建或运行截图。

### 1.1 原有接口与升级目标的区别

| 业务方面 | 原有后端情况 | 升级 A 对后端的新要求 |
|---|---|---|
| 商品出售 | `GET /api/products/current` 取当前一件商品；发布流程限制只能有一件在售 | 多商品可同时在售，按商品 ID 查询和展示商品列表 |
| 商品信息 | 主要包括名称、价格、描述、单张图片及状态 | 增加分类、库存、图片列表等数据 |
| 商品查询 | 当前商品与后台历史商品查询 | 增加关键词、二级分类与分页组合筛选 |
| 购买意向 | 提交买家姓名、联系方式、商品编号、备注 | 关联客户账号，增加购买数量与库存校验 |
| 交易完成 | 一笔成交后商品直接进入 `SOLD` 状态 | 成交按数量扣减库存；库存为 0 时停止销售 |
| 用户管理 | 主要只有卖家登录及修改密码 | 增加客户账号、登录认证、本人订单与商家客户查询 |

## 二、接口变更总览

按照**对外 HTTP 接口**统计，本次设计包含 **9 项新增接口、6 项原接口调整**。其中 A.1 对应商品管理，A.2 对应客户管理；部分订单和交易接口同时涉及两类需求。

### 2.1 新增接口

| 序号 | 请求方式 | 接口地址 | 新增功能 | 对应需求 |

| N03 | GET | `/api/categories/tree` | 查询两级商品分类树 | A.1 二级分类 |

## 三、新增接口详细说明

### 3.1 N01：商品列表与条件搜索

- **接口：** `GET /api/products`
- **对应需求：** A.1 多商品在售、分类筛选、商品搜索。
- **新增原因：** 原系统只提供“当前商品”入口，不满足同时展示多种商品的要求。
- **请求参数：** `keyword`（关键词，可选）、`categoryId`（分类 ID，可选）、`page`（页码）、`size`（每页条数）。
- **返回数据：** 商品编号、名称、价格、库存、分类、主图、状态，以及分页总条数。
- **业务处理：** 关键词和分类可组合筛选；分类筛选应明确是否包含子分类；买家列表原则上只返回可以展示的商品；参数错误时返回明确提示。

示例：

```http
GET /api/products?keyword=手机&categoryId=12&page=1&size=10
```

分页响应中可使用 `records`、`total`、`page`、`size`，便于前端直接渲染列表及分页控件。

### 3.2 N02：按商品编号查询详情

- **接口：** `GET /api/products/{id}`
- **对应需求：** A.1 多商品详情、库存和图片展示。
- **新增原因：** `/api/products/current` 默认只查询某一件商品，无法支撑商品列表中逐项查看。
- **路径参数：** `id` 为商品编号。
- **返回数据：** `id`、`name`、`description`、`price`、`stock`、`categoryId`、`images`、`status`。
- **业务处理：** 根据商品编号定位商品；不存在时返回“商品不存在”；非在售商品按业务要求返回状态，不允许继续购买。

### 3.3 N03：获取二级分类结构

- **接口：** `GET /api/categories/tree`
- **对应需求：** A.1 二级分类。
- **新增原因：** 旧版商品没有独立的二级分类查询入口。
- **请求参数：** 无。
- **返回数据：** 一级分类编号、名称，以及 `children` 二级分类数组。
- **业务处理：** 由后端按父子关系组织分类树；分类不存在时不能将无效编号绑定到商品。

例如“数码产品”作为一级分类，下设“手机”“电脑”等二级分类，便于搜索页面和商品发布页面共同使用。

### 3.4 N04：为商品添加多张图片

- **接口：** `POST /api/admin/products/{id}/images`
- **对应需求：** A.1 商品多图片。
- **新增原因：** 原有 `product.image_url` 只适合保存单张图片地址。
- **路径参数：** 商品编号 `id`。
- **请求体建议：** 图片地址 `imageUrl` 和排序值 `sortOrder`，允许多次调用追加图片。
- **返回数据：** 新增图片的编号、商品编号、地址和顺序。
- **业务处理：** 校验商品存在、图片地址不为空、排序值合法；图片记录应与商品建立一对多关联，不覆盖其他图片；后台接口需要卖家权限。

示例请求：

```json
{
  "imageUrl": "https://example.com/product-2.jpg",
  "sortOrder": 2
}
```

### 3.5 N05：客户注册

- **接口：** `POST /api/customers/register`
- **对应需求：** A.2 客户账户。
- **新增原因：** 旧版买家不需要登录，仅提交姓名与联系方式，无法形成可持续查询的客户身份。
- **请求体：** `username`、`password`、`phone`、`tradeLocation`（交易地点）。
- **返回数据：** 客户编号、用户名、注册结果；**不返回密码或密码哈希**。
- **业务处理：** 校验必填项和格式、用户名唯一性；密码通过 BCrypt 等安全哈希算法保存；重复用户名或非法字段返回清晰的错误信息。

示例请求：

```json
{
  "username": "buyer01",
  "password": "ExamplePassword123",
  "phone": "13800138000",
  "tradeLocation": "杭州"
}
```

### 3.6 N06：客户登录

- **接口：** `POST /api/customers/login`
- **对应需求：** A.2 客户身份认证。
- **请求体：** `username`、`password`。
- **返回数据：** 登录凭证、客户基本信息。
- **业务处理：** 查询客户账号、验证密码哈希；认证成功后生成由服务端验证的会话凭证；密码错误统一提示，不泄漏账号是否存在等敏感细节。
- **与原接口区别：** 原来只有卖家 `/api/admin/login` 与 `/api/seller/login`；买家身份应独立于卖家身份管理。

### 3.7 N07：客户查询本人历史订单

- **接口：** `GET /api/customers/me/orders`
- **对应需求：** A.2 个人历史订单。
- **请求参数：** `page`、`size`，可扩展状态筛选。
- **返回数据：** 订单编号、商品信息、购买数量、成交价格、订单状态、提交时间。
- **业务处理：** 客户身份从认证凭证中取得，不能通过随意填写 `customerId` 访问其他客户订单；查询结果按时间倒序并支持分页。

### 3.8 N08：商家查询客户列表

- **接口：** `GET /api/admin/customers`
- **对应需求：** A.2 商家客户管理。
- **请求参数：** 可选 `keyword`、`page`、`size`。
- **返回数据：** 客户编号、用户名、联系方式、注册时间等需要展示的信息。
- **业务处理：** 仅卖家可访问；不查询或输出密码哈希；支持按客户名筛选和分页，避免一次性查询全部数据。

### 3.9 N09：商家查询指定客户购买记录

- **接口：** `GET /api/admin/customers/{id}/orders`
- **对应需求：** A.2 商家查询客户历史购买记录。
- **路径参数：** 客户编号 `id`。
- **请求参数：** `page`、`size`。
- **返回数据：** 指定客户的订单列表和分页信息。
- **业务处理：** 检查卖家权限、客户是否存在；根据客户 ID 关联购买意向或订单记录；不应混入其他客户数据。

## 四、原有接口修改详细说明

### 4.1 M01：创建商品接口增加分类与库存

- **原接口：** `POST /api/admin/products`
- **原请求字段：** `name`、`description`、`imageUrl`、`price`。
- **修改内容：** 增加 `categoryId` 与 `stock`；多张图片由 N04 管理，创建接口可继续保留主图字段作兼容。
- **对应需求：** A.1 二级分类、库存管理。

修改后的建议请求：

```json
{
  "name": "蓝牙耳机",
  "description": "无线蓝牙耳机",
  "price": 199.00,
  "categoryId": 12,
  "stock": 20,
  "imageUrl": "https://example.com/main.jpg"
}
```

后端需要校验：名称和描述不为空、价格大于 0、分类有效、库存是非负整数。数据写入成功后返回商品编号，供后续添加图片或发布使用。

### 4.2 M02：发布商品接口取消单商品限制

- **原接口：** `POST /api/admin/products/{id}/publish`
- **原规则：** 新商品发布时，现有 `publish_product` 存储过程会检查是否已有在售或冻结商品；数据库 `uq_one_active_product` 唯一索引也限制同一时间只有一件有效商品。
- **修改内容：** 允许不同商品同时 `ON_SALE`；仍需防止同一商品重复发布，校验库存及商品状态。
- **对应需求：** A.1 多商品同时在售。

**这不是仅修改 Controller 就能完成的功能。** 还必须同步调整原唯一索引、`publish_product` 的旧规则，以及 `FacadeController.addProduct()` 中对已有在售商品数量的预检，否则接口即使放开，数据库或旧适配层仍会拒绝第二件商品发布。

### 4.3 M03：后台商品列表支持筛选与分页

- **原接口：** `GET /api/admin/products`
- **原行为：** 直接按创建时间获取商品历史列表。
- **修改内容：** 接收 `keyword`、`categoryId`、`status`、`page`、`size` 参数，支持多商品后台管理。
- **对应需求：** A.1 多商品、分类及搜索。
- **处理要求：** 分页结果包含记录总数；状态筛选能够区分在售、下架和售完等业务情况；列表查询不应因为数据量增长而一次返回所有记录。

### 4.4 M04：提交购买意向接口增加数量和客户关联

- **原接口：** `POST /api/intents`
- **原请求字段：** `productId`、`buyerName`、`contact`、`note`。
- **修改内容：** 增加 `quantity`；登录客户通过服务端身份识别并与意向记录关联，不再只依赖手填姓名和联系方式。
- **对应需求：** A.1 库存；A.2 客户身份与历史订单。

建议请求：

```json
{
  "productId": 101,
  "quantity": 2,
  "note": "周末交易"
}
```

后端应检查：商品可购买、数量大于 0、客户已认证，以及相应库存可支持本次交易。订单需保存购买数量和必要的价格快照；查询历史记录时才能正确还原当时的购买信息。

**库存处理口径：** 采用“提交意向时检查可购买性、实际成交时扣减库存”的设计。若业务要求提交时预占库存，应另行增加预占及释放逻辑，不能在两处重复扣减。

### 4.5 M05：交易完成接口增加库存扣减与售罄处理

- **原接口：** `POST /api/admin/trades/{id}/finish`
- **原请求字段：** `productId`、`success`、`reason`。
- **原行为：** 交易成功后整个商品直接进入 `SOLD`；失败时恢复 `ON_SALE`。
- **修改内容：** 根据意向数量扣减商品库存；剩余库存大于 0 时商品继续在售，库存为 0 时自动停止可购买；失败时不应扣减库存。
- **对应需求：** A.1 库存管理、库存清零下架与交易一致性。

成功交易应满足以下顺序：确认交易未结算、锁定对应商品或采用条件更新、核对库存、扣减数量、更新订单与交易状态；这些变更应保持事务一致。可通过“仅在库存充足时更新”的数据库条件避免并发超卖。重复确认同一交易必须被拒绝，不能再次扣减库存。

原 `finish_trade` 存储过程、单件商品 `FROZEN/SOLD` 状态规则以及“一件商品只能有一笔待处理交易”的约束也需要随多库存业务一起检查和调整。

### 4.6 M06：原“当前商品”接口转为兼容用途

- **原接口：** `GET /api/products/current`
- **原行为：** 从 `ON_SALE` 或 `FROZEN` 商品中选取一件并返回。
- **修改内容：** 原路径可暂时保留供旧页面兼容；商品列表统一使用 N01，商品详情统一使用 N02。
- **对应需求：** A.1 多商品展示。

旧前端仍存在 `/api/product/detail`、`/api/product/list`、`/api/product/add` 等适配接口，因此前后端联调时需要同步调整 `FacadeController` 的查询、字段映射和发布规则，避免新接口已支持多商品，而旧适配逻辑仍沿用单件商品设计。

## 五、接口改动与业务规则的对应关系

| 需求点 | 新增接口 | 调整接口 | 后端必须保证的规则 |
|---|---|---|---|
| A.1 多商品同时在售 | N01、N02 | M02、M06 | 不再按全系统唯一在售商品限制发布 |
| A.1 商品分类与搜索 | N03、N01 | M01、M03 | 分类有效、条件筛选正确、支持分页 |
| A.1 商品库存 | — | M01、M04、M05 | 数量合法、库存不为负、售罄停止销售 |
| A.1 商品多图 | N04、N02 | M01（保留主图兼容） | 图片与商品一对多关联，按顺序返回 |
| A.2 客户注册登录 | N05、N06 | — | 用户名唯一、密码安全保存、服务端认证 |
| A.2 客户历史订单 | N07 | M04 | 订单关联客户，客户只能查看本人记录 |
| A.2 商家查看客户购买记录 | N08、N09 | — | 商家权限校验，客户与订单对应准确 |

## 六、实现时需要同步处理的关键问题

### 6.1 数据结构与服务逻辑需要一起调整

升级后的接口需要有相应的数据字段与查询能力。建议在现有商品、意向和交易记录基础上补充：商品 `category_id`、`stock`；二级分类表；商品图片表；客户账号表；意向/订单 `customer_id`、`quantity`、成交价格快照等字段。

特别注意原数据库的 `uq_one_active_product`、`publish_product` 和交易冻结规则：如果继续保留旧版“只能有一件在售”的约束，新接口不能完成多商品发布。原有 `product.image_url` 可以作为主图兼容字段，多图片则通过独立关联表管理。

### 6.2 身份校验不能只靠前端页面

现有卖家后台代码说明中已标注 MVP 阶段暂缺真正的服务端鉴权，部分旧版登录 token 只用于前端登录态。新增客户接口和商家查询接口应明确区分客户与卖家身份；服务端每次查询个人订单或敏感后台数据时都应验证权限。

### 6.3 统一错误处理与返回结构

沿用项目的 `Result{code,message,data}`，业务错误可以针对“商品不存在、库存不足、用户名重复、账号密码错误、无权访问、重复结算”等情形提供稳定且清晰的错误消息。新接口的入参校验与 Service 层业务校验应互相配合，不应仅靠前端限制。

### 6.4 保持原有接口的联调兼容

当前仓库还包括 `FacadeController` 对旧前端路径的映射。新增商品搜索、客户登录和订单接口后，应保持前后端字段名称一致，避免出现后端返回 `quantity`、`stock`、`categoryId`，而旧页面仍只读取单商品状态的情况。

## 七、总结

本次需求升级 A 的后端接口工作可以归纳为三个方面：一是新增商品搜索、分类、多图片及客户账号、历史订单相关接口；二是修改商品发布、商品管理、购买意向和交易结算等原有接口；三是将原先围绕“单件商品”的规则调整为面向“多商品、多库存、可识别客户”的业务处理方式。

其中最重要的修改并不是新增 URL，而是**让接口参数、Service 业务校验、数据库约束和交易状态保持一致**。这样商品数量增加、客户开始登录以及订单与库存发生联动时，后端仍能保证查询正确、权限清晰、库存安全和交易结果一致。
